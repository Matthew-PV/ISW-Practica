# Catálogo de demostración de lugares para CS-50

**Fecha:** 2026-11-28 · **Historia:** CS-50, objetivo 4 · **Decidió:** Matthew-PV; implementación técnica a propuesta de Copilot

- **Contexto:** el contrato de lugares de [2026-11-26-lugares-y-mapa.md](./2026-11-26-lugares-y-mapa.md) necesita verificar en el servidor que cada lugar pertenece a la ciudad del plan. Para esta práctica se descarta la búsqueda externa y se reutiliza el catálogo de demostración existente, evitando depender de una licencia de proveedor aún no confirmada.
- **Decisión:**
  - El contrato HTTP se conserva: `GET /api/lugares/buscar?q=<texto>&ciudadId=<id>` devuelve como máximo 10 fichas con los campos acordados; `POST` y `PATCH` aceptan la lista de lugares; el detalle devuelve los lugares guardados con su `id`.
  - El catálogo canónico pasa a ser propiedad del backend, en `backend/data/lugares-madrid.json`. El frontend deja de mantener o leer una copia y consulta la API. El repositorio de lugares lee el catálogo; el servicio valida la ciudad y la lista; las rutas no acceden al fichero.
  - La búsqueda conserva el comportamiento actual: compara las palabras de `q`, sin distinguir mayúsculas ni tildes, con nombre, tipo y dirección. El catálogo actual cubre Madrid (España); las demás ciudades válidas no obtienen resultados de este catálogo.
  - Al crear o editar, el servidor valida cada `proveedorId` contra el catálogo y comprueba que la ciudad del plan coincide con la ciudad declarada por el catálogo. Usa los campos canónicos del catálogo para guardar la ficha, junto con la nota y la posición. No confía en nombre, dirección, coordenadas, imagen ni web modificables por el navegador. Si un ID no existe, la ciudad no coincide o cualquier dato de la lista es inválido, se rechaza la operación completa.
  - La relación de lugares del plan en MySQL es la persistencia de consulta y edición. Omitir `lugares` en una edición conserva la lista; `lugares: []` la vacía; enviar una lista sustituye la anterior en ese orden. Si cambia la ciudad y los lugares existentes dejan de pertenecer a ella, deben retirarse o sustituirse explícitamente.
  - `frontend/datos/lugares-planes.json` deja de ser un fallback de lectura y no se usa para persistir por título. Se conservan sus tres asociaciones de demostración, siete referencias de lugares, notas y orden como datos de seed normalizados: referencias `proveedorId`, notas y posiciones, asociadas mediante claves estables de los planes demo. Los `id` locales de ese fichero no se reutilizan; MySQL asigna los identificadores de las relaciones.
  - El objetivo 5 es independiente y queda pendiente: sustituir el catálogo de demostración por un proveedor externo. Esa integración es una ampliación futura y no forma parte de este cambio. El catálogo de demostración cubre la búsqueda mínima y la comprobación de ciudad necesarias para el objetivo 4; el contrato HTTP se conserva para facilitar la ampliación.
- **Alternativas:** mantener el JSON en el frontend y confiar en él al guardar (duplicaría el catálogo y permitiría falsificar fichas); continuar resolviendo lugares por título con `lugares-planes.json` (acopla datos de prueba al texto del plan y no conserva las ediciones); integrar un proveedor externo durante el objetivo 4 (añade dependencias y condiciones de uso antes de abordar el objetivo 5).
- **Consecuencias:** el catálogo actual tiene 21 lugares, IDs `demo-*` únicos y los campos obligatorios completos. `proveedorId` se conserva por compatibilidad con el contrato, pero en esta práctica identifica una entrada local de demostración, no un ID de un proveedor externo. El catálogo puede devolver `imagen` o `web` nulos. Las ciudades distintas de Madrid no disponen todavía de lugares de demostración. Las imágenes existentes enlazan a Wikimedia, pero el catálogo no conserva autoría ni licencia por imagen; hay que verificar y documentar esos datos antes de ampliar su uso público. La decisión no cambia Leaflet ni el mapa de OpenStreetMap.
